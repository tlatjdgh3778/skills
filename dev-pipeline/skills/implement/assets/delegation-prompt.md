# 작업 지시 조립 형식

Task마다 아래 형식으로 조립해 에이전트에게 전달한다. 저장하지 않는다. Task 전문과 스펙 항목 원문은 요약하지 말고 그대로 붙인다.

```
[스펙 경로]
<스펙 파일 경로>
인터페이스 계약(§4)과 엣지 케이스(§5)를 읽고 따른다.

[연결 항목 원문]
<Task의 연결 항목에 해당하는 스펙 줄을 스펙에서 그대로 붙인다. 예: "- DoD-2: ...", "- EC-1: ...">

[Task]
<계획의 해당 Task 전문>

[모드] (테스트 Task일 때만)
살 모드 — 골격 파일 <경로>의 case 본문만 채운다. `@spec`·`@given`·`@when`·`@then` 태그와 case 서술은 바꾸지 않는다. 골자가 틀렸다고 보이면 고치지 말고 NEEDS-DECISION으로 보고한다.

[규칙]
- Task의 `수정 대상` 밖과 `수정 금지`는 건드리지 않는다.
- 인터페이스 계약을 바꾸지 않는다. 변경이 필요하면 구현하지 말고 보고한다.
- 테스트 파일을 수정하지 않는다. 테스트가 실패하면 구현을 고친다. (테스트 Task를 받은 에이전트는 Task가 지정한 테스트 파일만 작성하며, 테스트를 실행하지 않는다)
- 실패를 숨기기 위한 skip·기대 결과 완화·검사 설정 변경을 하지 않는다.
- 다른 에이전트를 만들거나 위임하지 않는다.
- 스펙과 Task에 없는 결정을 추측하지 않는다. 막히면 보고한다.

[보고]
구현 완료 후 다음만 간결하게 보고한다. 첫 줄은 반드시 `STATUS: IMPLEMENTED | BLOCKED | NEEDS-DECISION` 형식으로 쓴다.
- 수정한 파일 목록
- 연결 항목별 처리: 항목 ID → 구현·테스트 위치(`파일:라인`). 처리하지 못한 항목은 사유
- Task의 실행 명령과 그 결과(lint·typecheck·관련 테스트별로 통과·실패·미실행)
- 스펙·Task와 달라진 점 (없으면 "없음")
- BLOCKED·NEEDS-DECISION이면 근거와 필요한 조치·결정
```
