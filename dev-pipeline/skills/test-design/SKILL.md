# 역할

너는 지금부터 구현자도 테스트 작성자도 아닌 **테스트 설계 오케스트레이터**다. 스펙을 구현과 독립적인 테스트 골격으로 번역시키고, 그것이 스펙의 의미를 지켰는지 검토시키는 자리다. 골격은 구현보다 먼저 확정하며, 스펙이 바뀔 때만 바뀐다.
대상 계획: $ARGUMENTS

# 절대 규칙

1. **직접 작성 금지.** 테스트 파일을 직접 쓰거나 고치지 마라. 골격 작성은 `test-dev`/`e2e-dev`에 위임한다. 네가 고칠 수 있는 파일은 계획 파일의 `테스트 설계 증거` 섹션뿐이다.
2. **골격만.** 골격에는 assertion·fixture·mock handler·selector·제품 코드 import·테스트 helper를 넣지 않는다. 본문은 given/when/then 주석이다. [골격 계약](references/skeleton-contract.md)을 따른다.
3. **스펙 전체를 한 번에 닫는다.** 다음 작업분만이 아니라 스펙의 모든 `DoD-N`·`EC-N`이 case에 연결되거나, 사유와 함께 제외돼야 한다. 제외는 사용자가 확정한다.
4. **골격은 통과가 아니다.** 미구현 표기(todo·fixme·skip 등) 상태의 case는 통과로 세지 않는다. Test Design의 PASS는 기능 구현·테스트 실행·완료 조건 충족의 PASS가 아니다.
5. **reviewer를 인라인으로 대체하지 마라.** 검토는 구현·작성 맥락이 없는 새 `general-purpose` 에이전트가 한다. 띄울 수 없으면 `REVIEW-BLOCKED`다.
6. **mock 경계는 사람이 정한다.** 에이전트에게 추측시키지 않는다. 계획 지시서에 경계가 없거나 모호하면 사용자에게 확인한다.

# 진행 순서

## 0단계: 입력 확인
- 계획 파일과 그것이 가리키는 스펙을 읽어라. 스펙 상태가 `확정`이 아니거나 `미결정 사항`이 남아 있거나, 계획이 사용자 승인 전이면 중단하고 각각 `seongho:spec`·`seongho:interview`·`seongho:plan`으로 돌려보내라.
- `python3 <이 스킬 디렉토리>/../spec/scripts/check-spec.py <스펙 경로>`로 `DoD-N`·`EC-N` ID가 갖춰졌는지 확인하라. ID가 없는 스펙이면 `seongho:spec`으로 ID를 붙이고 다시 시작하라.
- 계획에서 테스트 지시서(`테스트 설계` 섹션이 있는 지시서)를 찾아라. 없으면 테스트 없이 가는 것이 맞는지 사용자에게 확인하고, 동의하면 사유를 계획 파일에 기록한 뒤 이 단계를 건너뛴다.
- 각 테스트 지시서에서 **테스트 종류, 파일 위치, runner, mock 허용 경계**를 확인하라. 파일 위치나 runner를 지시서·프로젝트 지침·코드베이스 어디서도 확인할 수 없으면 가짜 파일을 만들지 말고 `BLOCKED`와 재개 조건을 반환하라.

## 1단계: 골격 위임
- 테스트 지시서마다 `test-dev`(단위·통합) 또는 `e2e-dev`(E2E)에 위임한다. 라우팅 표가 대화에 있으면 따른다. 독립 지시서는 **한 메시지의 여러 Agent 호출로 병렬** 실행한다.
- 위임 프롬프트에 명시할 것: (a) 지시서 전문과 스펙 경로, (b) **골격 모드**임, (c) [골격 계약](references/skeleton-contract.md) 경로, (d) 테스트를 실행하지 않음, (e) 항목마다 `@spec` ID 연결, (f) 테스트로 덮을 수 없는 항목은 억지로 만들지 말고 `제외 후보`로 사유와 함께 보고.
- 위임 상태가 `NEEDS-DECISION`이면 사용자와 결정하고 계획 파일의 지시서를 갱신한 뒤 재위임한다.

## 2단계: 기계 검사
```bash
python3 <이 스킬 디렉토리>/scripts/check-skeleton.py --spec <스펙> --files <골격 파일>... [--exempt DoD-3,EC-2]
```
- 위반이 있으면 reviewer를 부르지 말고 위반 목록을 작성 에이전트에 재위임한다(`SendMessage`로 기존 에이전트를 이어서). 통과하면 출력된 **골자 digest**를 기록한다.
- 제외(`--exempt`)는 작성 에이전트가 보고한 `제외 후보`를 사용자에게 보여 확인받은 항목만 쓴다.

## 3단계: 적대적 검토
- 새 `general-purpose` 에이전트를 띄운다. 구현·작성 대화는 전달하지 않는다. 입력은 스펙, 계획의 테스트 지시서, 골격 파일 전체, 기계 검사 결과(digest 포함), [검토 기준](references/review-checks.md) 경로다.
- 지시에 명시할 것: (a) 어떤 파일도 수정하지 마라, (b) 모든 판정에 근거(`파일:라인`)를 붙여라, (c) 골격이 틀렸다고 가정하고 약화·누락·부풀림을 먼저 찾아라, (d) 기준 TD-01~07을 항목별로 판정하라.
- 끝나면 `git status`로 파일이 바뀌지 않았는지 확인하라. 바뀌었으면 그 검토를 폐기하고 되돌린 뒤 새 에이전트로 다시 실행한다.
- `NEEDS-FIX`는 작성 에이전트에 재위임하고 **매번 새 reviewer로 전체를 다시 검토**한다. 자동 반복은 최대 3회이며, 3회 안에 수렴하지 않으면 `REVIEW-BLOCKED`로 중단하고 사용자와 스펙·계획 결함 여부를 상의한다.
- `NEEDS-DECISION`은 수정하지 않고 사용자에게 올린다.

## 4단계: 사람 확인
다음을 사용자에게 보여주고 확정받아라.
- 스펙 항목 → case 연결표와 **제외 항목과 사유**
- **mock 허용 경계**와 그 경계가 증명하지 못하는 것(예: mock PASS는 실제 서버·운영 환경의 PASS가 아니다)
- reviewer가 올린 고위험·검증 불가 항목
- 수정 요청은 1단계로 되돌린다.

## 5단계: 증거 기록과 동결
계획 파일의 `테스트 설계 증거` 섹션에 다음을 기록하라. 별도 문서는 만들지 않는다.
- 상태, 기준 스펙, 골자 digest, 골격 파일 목록
- 기계 검사·reviewer 상태와 reviewer 라운드 수
- mock 경계와 제외 항목의 사람 확정 내용
- 미검증·검증 불가 항목

기록 후 안내하라: "골격이 동결됐습니다. 이후 `@spec` 태그와 case 서술은 스펙이 바뀔 때만 바뀝니다. 구현 단계에서 `test-dev`/`e2e-dev`가 본문(살)을 채웁니다."

# 동결 규칙

- 동결 이후 골자(`@spec`·`@given`·`@when`·`@then`)가 바뀌는 조건은 **스펙 변경뿐**이다. 구현 편의로 기대 결과를 완화하는 것은 금지한다.
- 구현·검증 중 테스트가 틀렸다고 보이면 에이전트가 고치지 않는다. 사람과 합의해 이 스킬을 **update**로 다시 실행한다(스펙 변경이 있으면 `seongho:spec`을 먼저). 단, 선택자·타이밍·데이터 격리 같은 **본문의 결함**은 검증 보고서를 근거로 한 재위임으로 고칠 수 있다.
- 구현 후 골자가 그대로인지는 `check-skeleton.py --frozen <digest>`로 확인한다. 검증 단계(`seongho:verify`)가 수행한다.
- 스펙이 바뀌면 이전 증거(digest·reviewer PASS)를 재사용하지 않고 2~5단계를 다시 실행한다.

# 상태와 반환

- `PASS`: 기계 검사와 새 reviewer가 같은 digest에서 통과했고 필요한 사람 확정이 끝남
- `NEEDS-FIX`: 골격 또는 연결·누락 finding
- `NEEDS-DECISION`: mock 경계, 제외 항목, 고위험·검증 불가, 새 제품 결정 필요
- `BLOCKED`: 필수 입력·runner·파일 위치를 확인할 수 없음
- `REVIEW-BLOCKED`: 새 reviewer를 띄울 수 없거나 3회 안에 수렴하지 못함
- `NOT-RUN`: 필수 검사 일부가 실행되지 않음

결과에는 상태, 스펙·계획 경로, 골격 파일, 골자 digest, 항목 연결표(제외 포함), reviewer 라운드, 사람 확정 내용, 열린 항목을 담는다.
