# 개발 파이프라인 (10단계)

이 스킬을 실행하는 세션은 **오케스트레이터**다. 직접 코드를 작성하지 않는다. 인터뷰·계획·위임·취합·사용자 확인만 담당하고, 실제 구현과 검증은 서브 에이전트가 수행한다.

**스킬 호출 규칙.** 다른 스킬은 Skill 도구로 `seongho:<스킬 이름>`(예: `seongho:spec`)을 호출한다. 접두사 없는 이름은 다른 스킬과 충돌할 수 있다(`verify`가 실제로 그랬다). 서브 에이전트에게 스킬을 쓰게 할 때도 같은 이름을 적는다.

각 단계는 순서대로 진행하되, 사용자가 특정 단계부터 시작을 지시하면(예: 이미 스펙이 있음) 그 단계로 건너뛴다. 단계 전환마다 현재 단계 번호와 다음 행동을 한 줄로 알린다.

## 프로젝트 지식

이 스킬은 프로젝트 지식을 갖지 않는다. 스택, 명령, 규칙, 커밋 관례는 프로젝트의 `CLAUDE.md`, `AGENTS.md`, `README`와 코드베이스에서 확인한다. 하위 스킬과 에이전트도 같은 곳에서 읽는다.

## 에이전트 라우팅

**영역에 맞는 전용 에이전트가 있으면 반드시 그 에이전트를 쓴다.** 구현·테스트 작성 에이전트는 사용 가능한 에이전트 목록과 `description`으로 고르고(플러그인으로 설치하면 이름에 `seongho:backend-dev`처럼 접두사가 붙는다), 프로젝트 지침 파일에 라우팅 지침이 있으면 그것을 따른다. 맞는 에이전트가 없으면 `general-purpose`를 쓰고 그 사실을 보고한다.

| 역할 | 에이전트 | 단계 |
|---|---|---|
| 탐색 | 내장 `Explore` (병렬 fan-out) | 2 |
| 계획 | 내장 `Plan` (`plan` 스킬이 호출) | 4 |
| 테스트 골격 작성 | `test-dev`(단위·통합), `e2e-dev`(E2E) — 골격 모드, 작성 전용 | 5 |
| 골격 검토 | 새 `general-purpose` 에이전트 (`test-design` 스킬이 호출) | 5 |
| 구현 | `backend-dev`, `frontend-dev` | 6 |
| 테스트 본문 채우기 | `test-dev`, `e2e-dev` — 살 모드, 작성 전용, 실행하지 않음 | 6 |
| 적대적 검증 | 새 `general-purpose` 에이전트 + `verify` 스킬 | 7 |
| 부검 | 새 `general-purpose` 에이전트 | 10 |

## 1단계: 요청 확보
- `$ARGUMENTS`를 입력으로 삼는다. 없으면 "구현하려는 것을 한 줄로" 요청한다.
- 어느 영역(패키지·앱)에 걸치는 작업인지 1차 추정만 하고(확정 금지) 즉시 2단계로 넘어간다.

## 2단계: 요구 정제 (인터뷰)
- 인터뷰 전에 **Explore 에이전트를 한 메시지에 병렬로** 띄워 탐색한다. 축은 관련 모듈, 기존 패턴, 충돌 지점, 테스트 현황이다. 탐색 결과가 대화에 올라온 뒤 Skill 도구로 `seongho:interview`를 호출하고, 인터뷰의 0단계 탐색은 이 결과를 사용하게 한다. 인터뷰 중 추가 탐색이 필요하면 같은 방식으로 병렬 취합한다.
- 규칙(구현 금지, 한 번에 한 주제, 답을 받아야 전진)은 `interview` 스킬이 정의한다.
- 결산 확인(결정 목록 + 사용자 확인)이 끝나야 3단계로 간다.

## 3단계: 스펙
- Skill 도구로 `seongho:spec`을 호출해 결산을 다섯 장기 구조의 스펙으로 굳힌다. 저장 경로는 `spec` 스킬이 정하며, 이후 단계에는 그 경로를 인자로 넘긴다.
- 스펙에 `미결정 사항`이 남으면 4단계로 가지 말고 2단계로 돌아간다.

## 4단계: 계획 (Task)
- Skill 도구로 `seongho:plan`을 스펙 경로 인자와 함께 호출한다. 산출은 사이드별 Task와 의존 순서, 항목 coverage가 담긴 계획 파일 하나이며, 사용자 승인 후 5단계(테스트 설계)로 간다. 에이전트에게 줄 지시서는 저장하지 않고, 어느 에이전트에 맡길지와 작업 지시 조립은 5·6단계가 위임할 때 정한다.

## 5단계: 테스트 설계 (골격 동결)
- Skill 도구로 `seongho:test-design`을 계획 파일 경로 인자와 함께 호출한다. 스펙의 `DoD-N`·`EC-N` 항목을 구현 전에 테스트 골격(describe/it 조건 서술, 본문은 given/when/then 주석)으로 고정한다. 골격은 `test-dev`/`e2e-dev`가 골격 모드로 작성하고, 기계 검사와 새 `general-purpose` reviewer의 적대적 검토를 거친다.
- **mock 허용 경계와 테스트로 덮지 않는 항목은 사용자가 확정한다.** 에이전트에게 맡기지 않는다.
- 통과하면 골자 digest가 계획 파일의 `테스트 설계 증거`에 기록되고 골격이 동결된다. 이후 골자는 스펙이 바뀔 때만 바뀐다.
- 테스트 없이 진행하려면 사용자 동의와 사유 기록이 필요하다. 작은 변경이라면 사용자가 이 단계를 건너뛰도록 지시할 수 있다.

## 6단계: 구현 (멀티 에이전트)
- 시작할 때 스펙의 `상태`를 `구현중`으로 갱신한다.
- Skill 도구로 `seongho:implement`를 계획 파일 경로 인자와 함께 호출한다. Task를 작업 지시로 조립해 에이전트에 위임하며, 독립 Task는 **한 메시지의 여러 Agent 호출로 병렬**, 의존이 있으면 순차로 진행한다.
- 테스트 Task(`test-dev`, `e2e-dev`)는 이 단계에서 동결된 골격의 **본문(살)만** 채운다. 골자는 바꾸지 못하고, 작성만 하고 실행하지 않는다. 의존 순서는 계획 파일을 따른다(예: 화면이 있어야 E2E의 살을 채울 수 있다).
- 끝나면 취합 결과(담당 에이전트, 수정 파일, 자체 검사, 골자 동결 확인, 달라진 점)를 확인하고 7단계로 간다.

## 7단계: 검증 (적대적 검증자)
**원칙: 코드를 생성한 에이전트는 자기 코드를 검증할 수 없다. 테스트를 만든 에이전트는 그 테스트를 실행·판정하지 않는다.**
- 새 `general-purpose` 에이전트를 띄워 Skill 도구로 `seongho:verify`를 `<스펙 경로> <계획 파일 경로>` 인자로 호출해 수행시키고, 결과에 따라 6↔7을 반복한다. 계획 파일 경로로 골자 digest를 확인해 테스트 변조를 잡는다.
- 지시 방법, 읽기 전용 확인, 결과 처리 규칙은 [검증 루프](references/verification-loop.md)를 읽고 따른다.

## 8단계: 사용자 최종 검토
- 제시: (a) 스펙 대조 요약(충족/부분 충족/미충족/검증 불가, 스코프 초과·스펙 드리프트), (b) 수정 파일과 핵심 diff 요약, (c) 테스트 결과와 **미검증 범위**.
- 승인이 있어야 9단계로 간다. 수정 요청은 6단계로 되돌린다(스펙이 바뀌면 3단계, 골자 변경이 필요하면 5단계).

## 9단계: 커밋 및 추적
- 사용자 승인 후에만 커밋한다. 규칙은 [커밋과 되돌리기](references/commit-and-revert.md)를 읽고 따른다.
- 스펙 상태를 `구현중 → 완료`로 갱신한다.

## 10단계: 부검 (문제가 발생했을 때만)
- 배포 이후나 검증 이후 문제가 발견됐을 때만 실행한다. 절차는 [부검](references/postmortem.md)을 읽고 따른다. 부검 후 수정본의 최종 검토·커밋까지 이 단계에 포함된다.

## 요약 플로우
```
요청 → (병렬 Explore) → interview → spec(DoD-N·EC-N) → plan(Task)
    → test-design [test-dev · e2e-dev 골격 작성 → 기계 검사 → 새 reviewer → mock 경계 사람 확정 → 골격 동결]
    → implement [backend-dev → frontend-dev | test-dev · e2e-dev 본문 채우기(작성 전용)]
    → 새 general-purpose + verify (적대적 검증 + 골격 동결 확인 + 테스트 실행)  ←── 실패 시 원 구현 에이전트로 루프
    → 사용자 검토 → 커밋
    → (문제 시) revert → 부검(general-purpose) → 스킬·에이전트 개선 → 수정 → 재검증 → 최종 검토 → 커밋
```
