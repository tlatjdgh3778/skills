# 개발 파이프라인 (10단계)

이 스킬을 실행하는 세션은 **오케스트레이터**다. 직접 코드를 작성하지 않는다. 인터뷰·계획·위임·취합·사용자 확인만 담당하고, 실제 구현과 검증은 서브 에이전트가 수행한다.

**스킬 호출 규칙.** 다른 스킬은 Skill 도구로 `seongho:<스킬 이름>`(예: `seongho:spec`)을 호출한다. 접두사 없는 이름은 다른 스킬과 충돌할 수 있다(`verify`가 실제로 그랬다). 서브 에이전트에게 스킬을 쓰게 할 때도 같은 이름을 적는다.

각 단계는 순서대로 진행하되, 사용자가 특정 단계부터 시작을 지시하면(예: 이미 스펙이 있음) 그 단계로 건너뛴다. 단계 전환마다 현재 단계 번호와 다음 행동을 한 줄로 알린다.

## 수정 요청과 재개

수정 요청은 **영향받는 가장 이른 단계**부터 재개한다.

| 변경 | 재개 단계 |
|---|---|
| 요구사항·인터페이스 계약 | 2~3단계. 스펙을 갱신·재확정한다. |
| 계획·작업 범위 | 4단계 |
| 테스트 행동 기준(골자) | 5단계 (`seongho:test-design` update) |
| 승인된 기준을 유지하는 구현·테스트 코드 오류 | 6단계 |

기준을 바꾸면 관련 스펙·계획·골격을 먼저 갱신하고 전체를 다시 승인받지 않고 영향받는 부분만 반영한다.

**완료된 기능의 수정이 승인되면** 오케스트레이터가 영향받는 Task만 `대기`로 되돌린다. 기대 동작을 유지한 채 4~5단계부터 재개하면 스펙 상태를 `확정`, 6단계로 바로 재개하면 `구현중`으로 갱신한다. 요구사항·계약이 바뀌면 2~3단계의 스펙 재확정을 먼저 한다. 6단계에 착수하면 스펙은 `구현중`, 대상 Task는 `진행`으로 기록한다. 이전 완료·검증·수정 이력은 지우지 않고 보존한다.

## 프로젝트 지식

이 스킬은 프로젝트 지식을 갖지 않는다. 스택, 명령, 규칙, 커밋 관례는 프로젝트의 `CLAUDE.md`, `README`와 코드베이스에서 확인한다. 하위 스킬과 에이전트도 같은 곳에서 읽는다.

## 에이전트 라우팅

**영역에 맞는 전용 에이전트가 있으면 반드시 그 에이전트를 쓴다.** 구현·테스트 작성 에이전트는 사용 가능한 에이전트 목록과 `description`으로 고르고(플러그인으로 설치하면 이름에 `seongho:backend-dev`처럼 접두사가 붙는다), 프로젝트 지침 파일에 라우팅 지침이 있으면 그것을 따른다. 맞는 에이전트가 없으면 `general-purpose`를 쓰고 그 사실을 보고한다.

| 역할 | 에이전트 | 단계 |
|---|---|---|
| 탐색 | 내장 `Explore` (병렬 fan-out) | 2 |
| 계획 | 내장 `Plan` (`plan` 스킬이 호출) | 4 |
| 테스트 골격 작성 | `test-dev`(단위·통합), `e2e-dev`(E2E) — 골격 모드, 작성 전용 | 5 |
| 골격 검토 | 새 `general-purpose` 에이전트 (`test-design` 스킬이 호출) | 5 |
| 구현 | `backend-dev`, `frontend-dev` | 6 |
| 테스트 본문 채우기 | `test-dev`, `e2e-dev` — 살 모드, 작성 전용, 실행하지 않음 | 6 |
| 적대적 스펙 대조(읽기 전용) | 새 `general-purpose` 에이전트 + `verify` 스킬 | 7 |
| 단위·통합 테스트·정합성 명령 실행 | `test-runner` (실행 전용) | 7 |
| E2E·브라우저 시나리오 실행 | `e2e-runner` (실행 전용) | 7 |
| 커밋 메시지·세션 기록 | `seongho:git-commit-rules` 스킬 (부모가 실행) | 9 |
| 부검 | 새 `general-purpose` 에이전트 | 10 |

## 스킬·에이전트 관계

```text
seongho:interview
  ├─ Explore 에이전트 (병렬)
  │   관련 코드·문서·기존 패턴·충돌·테스트 현황 조사
  └─ 부모 → 조사 결과로 사용자 인터뷰·요구사항 확정
  ↓
seongho:spec
  ↓
seongho:plan
  ├─ 내장 Plan 에이전트 (읽기 전용, 계획만 반환)
  └─ 부모 → 계획 정리·사용자 승인·계획 파일 저장
  ↓
seongho:test-design
  ├─ test-dev · e2e-dev            [골격 모드, 작성 전용]
  ├─ 새 general-purpose           [골격 적대적 검토]
  └─ 확정 스펙 + 승인된 계획 파일 → 테스트 골격 (mock 경계는 사용자 확정)
  ↓
seongho:implement
  ├─ backend-dev · frontend-dev   [구현 전용]
  └─ test-dev · e2e-dev           [살 모드, 작성 전용, 실행하지 않음]
  ↓
독립 검증                              [부모가 직접 위임·취합, 모두 읽기 전용]
  ├─ 새 general-purpose + seongho:verify   [스펙·코드·assertion 대조, 실행하지 않음]
  ├─ test-runner                           [단위·통합 테스트·정합성 명령 실행]
  └─ e2e-runner                            [E2E·브라우저 시나리오 실행]
  ↓
사용자 최종 승인 → 스펙 상태 완료 반영 → 커밋
  ↓ 문제가 발생한 경우
새 general-purpose (부검)
  └─ 부모 → 보고서 저장·사용자 개선안 검토
  ↓ 개선안 승인
필요한 기준 갱신 (2~5단계) → 수정·검증·승인·커밋 (6~9단계)
```

- 검증 실패는 부모가 원인을 분류해 해당 단계로 반환한다. 구현 오류는 `seongho:implement`의 원 작성 에이전트가 수정하고, 스펙·계획·골자 결함은 해당 선행 단계로 돌려 갱신한 뒤 7단계를 다시 수행한다.
- 인터뷰 진행, 스펙 본문 작성, 계획 정리·저장, 결과 취합·상태 갱신, 사용자 확인, 보고서 저장은 해당 스킬을 실행하는 부모가 맡는다. 부모는 코드를 작성하지 않는다.
- 검토·검증·부검 역할은 작성자와 다른 새 인스턴스로 실행하고 작성 대화를 물려주지 않는다. 제품·테스트 수정은 원 작성 에이전트에 반환한다.
- 읽기 전용 역할(`Plan`, `verify` 검증자, `test-runner`, `e2e-runner`, 부검 에이전트)은 코드·스펙·상태를 수정하지 않는다. 대조와 실행을 한 역할이 하지 않는다.

## 1단계: 요청 확보
- `$ARGUMENTS`를 입력으로 삼는다. 없으면 "구현하려는 것을 한 줄로" 요청한다.
- 어느 영역(패키지·앱)에 걸치는 작업인지 1차 추정만 하고(확정 금지) 즉시 2단계로 넘어간다.

## 2단계: 요구 정제 (인터뷰)
- 인터뷰 전에 **Explore 에이전트를 한 메시지에 병렬로** 띄워 탐색한다. 축은 관련 모듈, 기존 패턴, 충돌 지점, 테스트 현황이다. 탐색 결과가 대화에 올라온 뒤 Skill 도구로 `seongho:interview`를 호출하고, 인터뷰의 0단계 탐색은 이 결과를 사용하게 한다. 인터뷰 중 추가 탐색이 필요하면 같은 방식으로 병렬 취합한다.
- 규칙(구현 금지, 한 번에 한 주제, 답을 받아야 전진)은 `interview` 스킬이 정의한다.
- 결산 확인(결정 목록 + 사용자 확인)이 끝나야 3단계로 간다.

## 3단계: 스펙
- Skill 도구로 `seongho:spec`을 호출해 결산을 다섯 장기 구조의 스펙으로 굳힌다. 저장 경로는 `spec` 스킬이 정하며, 이후 단계에는 그 경로를 인자로 넘긴다.
- 스펙에 `미결정 사항`이 남으면 4단계로 가지 말고 2단계로 돌아간다.

## 4단계: 계획 (Task)
- Skill 도구로 `seongho:plan`을 스펙 경로 인자와 함께 호출한다. 산출은 사이드별 Task와 의존 순서, 항목 coverage가 담긴 계획 파일 하나이며, 사용자 승인 후 5단계(테스트 설계)로 간다. 에이전트에게 줄 지시서는 저장하지 않고, 어느 에이전트에 맡길지와 작업 지시 조립은 5·6단계가 위임할 때 정한다.

## 5단계: 테스트 설계 (골격 동결)
- Skill 도구로 `seongho:test-design`을 계획 파일 경로 인자와 함께 호출한다. 스펙의 `DoD-N`·`EC-N` 항목을 구현 전에 테스트 골격(describe/it 조건 서술, 본문은 given/when/then 주석)으로 고정한다. 골격은 `test-dev`/`e2e-dev`가 골격 모드로 작성하고, 기계 검사와 새 `general-purpose` reviewer의 적대적 검토를 거친다.
- **mock 허용 경계와 테스트로 덮지 않는 항목은 사용자가 확정한다.** 에이전트에게 맡기지 않는다.
- 통과하면 골자 digest가 계획 파일의 `테스트 설계 증거`에 기록되고 골격이 동결된다. 이후 골자는 스펙이 바뀔 때만 바뀐다.
- 테스트 없이 진행하려면 사용자 동의와 사유 기록이 필요하다. 작은 변경이라면 사용자가 이 단계를 건너뛰도록 지시할 수 있다.

## 6단계: 구현 (멀티 에이전트)
- 시작할 때 스펙의 `상태`를 `구현중`으로 갱신한다.
- Skill 도구로 `seongho:implement`를 계획 파일 경로 인자와 함께 호출한다. Task를 작업 지시로 조립해 에이전트에 위임하며, 독립 Task는 **한 메시지의 여러 Agent 호출로 병렬**, 의존이 있으면 순차로 진행한다.
- 테스트 Task(`test-dev`, `e2e-dev`)는 이 단계에서 동결된 골격의 **본문(살)만** 채운다. 골자는 바꾸지 못하고, 작성만 하고 실행하지 않는다. 의존 순서는 계획 파일을 따른다(예: 화면이 있어야 E2E의 살을 채울 수 있다).
- 끝나면 취합 결과(담당 에이전트, 수정 파일, 자체 검사, 골자 동결 확인, 달라진 점)를 확인하고 7단계로 간다.

## 7단계: 검증 (스펙 대조 + 테스트 실행)
**원칙: 코드를 생성한 에이전트는 자기 코드를 검증할 수 없다. 테스트를 만든 에이전트는 그 테스트를 실행·판정하지 않는다.** 검증 역할은 모두 새 인스턴스이고 구현 대화를 물려받지 않으며, 같은 코드 기준을 대상으로 한다. 검증 중에는 대상 코드와 테스트를 바꾸지 않는다.
- **스펙 대조:** 새 `general-purpose` 에이전트가 Skill 도구로 `seongho:verify`를 `<스펙 경로> <계획 파일 경로>` 인자로 실행한다. 코드·테스트 assertion을 스펙에 대조하며 **아무것도 실행하지 않는다.** 계획 파일 경로로 골자 digest를 확인해 테스트 변조를 잡는다.
- **테스트 실행:** `test-runner` 에이전트에 계획의 실행 명령과 프로젝트의 정합성 명령을 전달해 실행시킨다.
- **E2E 실행:** E2E Task나 시나리오가 있으면 `e2e-runner` 에이전트에 승인된 시나리오(대상 환경, 사전 조건, 사용자 행동, 기대 결과, 연결 항목, mock 범위)를 전달해 실행시킨다.
- 서로 간섭하지 않는 검증은 **한 메시지의 여러 Agent 호출로 병렬** 실행한다. 공유 서버·계정·데이터를 쓰는 검증은 순차로 돌린다.
- 오케스트레이터가 세 결과를 항목별로 취합하고, 결과에 따라 6↔7을 반복한다. 지시 방법, 읽기 전용 확인, 취합·결과 처리 규칙은 [검증 루프](references/verification-loop.md)를 읽고 따른다.

## 8단계: 사용자 최종 검토
- 제시: (a) 스펙 대조 요약(충족/부분 충족/미충족/검증 불가, 스코프 초과·스펙 드리프트), (b) 수정 파일과 핵심 diff 요약, (c) 테스트 결과와 **미검증 범위**.
- 승인이 있어야 9단계로 간다. 수정 요청은 위 [수정 요청과 재개](#수정-요청과-재개) 표에 따라 영향받는 단계로 되돌린다. 승인된 기준을 유지하는 구현 수정만 6단계로 바로 돌아간다.

## 9단계: 커밋 및 추적
- 사용자 승인 후에만 커밋한다. 규칙은 [커밋과 되돌리기](references/commit-and-revert.md)를 읽고 따른다.
- 스펙 상태를 `구현중 → 완료`로 갱신한다. 상태 갱신은 커밋 **전에** 해서 완료 상태와 구현 변경이 같은 커밋에 남게 한다.
- Skill 도구로 `seongho:git-commit-rules`를 호출해 메시지 작성과 `Session` 트레일러가 붙은 커밋까지 진행한다. 세션 ID를 확보하지 못해 스크립트가 차단하면 커밋하지 않고 사용자에게 알린다.

## 10단계: 부검 (문제가 발생했을 때만)
- 배포 이후나 검증 이후 문제가 발견됐을 때만 실행한다. 절차는 [부검](references/postmortem.md)을 읽고 따른다. 부검 후 수정본의 최종 검토·커밋까지 이 단계에 포함된다.

## 요약 플로우
