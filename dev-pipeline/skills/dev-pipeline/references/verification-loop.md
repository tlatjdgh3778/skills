# 검증 루프 (7단계)

검증은 역할 셋으로 나뉜다. 모두 새 에이전트이고 구현 대화를 전달하지 않으며, 같은 코드 기준을 대상으로 한다.

| 역할 | 에이전트 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| 스펙 대조 | 새 `general-purpose` + `seongho:verify` | 스펙을 코드·테스트 assertion에 대조, 골자 digest 확인, 적대적 수색 | 어떤 것도 실행하지 않는다 |
| 테스트 실행 | `test-runner` | 계획의 실행 명령과 프로젝트의 정합성 명령(빌드·타입 검사·린트·테스트) 실행 | 코드·테스트를 고치지 않는다. 원인을 해석해 결함을 분류하지 않는다 |
| E2E 실행 | `e2e-runner` | 승인된 시나리오를 실제 화면에서 실행, 증거 수집 | 코드·테스트를 고치지 않는다 |

## 위임 지시
- **스펙 대조:** Skill 도구로 `seongho:verify`를 `<스펙 경로> <계획 파일 경로>` 인자로 호출하게 한다. 지시에 명시할 것: (a) 어떤 파일도 수정·실행하지 마라, (b) 모든 판정에 근거를 붙여라, (c) 구현을 신뢰하지 말고 깨뜨릴 방법을 먼저 찾아라. 계획 파일 경로를 주는 이유는 `테스트 설계 증거`의 골자 digest로 테스트 골자가 동결 상태 그대로인지 확인시키기 위해서다.
- **테스트 실행:** 코드 기준(커밋 또는 작업 트리), 계획의 Task별 `실행 명령`, 프로젝트의 정합성 명령(없으면 찾을 곳)을 전달한다.
- **E2E 실행:** 대상 URL·환경, 사전 조건·필요 데이터, 사용자 행동, 기대 결과와 연결 항목(`DoD-N`·`EC-N`), mock과 실제 연동의 범위가 담긴 승인된 시나리오를 전달한다. E2E Task가 없고 시나리오도 없으면 이 역할은 생략하고 사유를 기록한다.
- 서로 간섭하지 않는 역할은 **한 메시지의 여러 Agent 호출로 병렬** 실행한다. 공유 서버·계정·데이터를 쓰는 역할(예: 테스트와 E2E가 같은 DB를 쓴다)은 순차로 실행한다.

## 읽기 전용 확인
읽기 전용은 지시와 도구 제한으로 보장하므로, 모든 검증이 끝나면 `git status`로 대상 파일이 바뀌지 않았는지 확인한다. 바뀐 파일이 있으면 그 검증 결과를 폐기하고 되돌린 뒤 새 에이전트로 다시 실행한다. 검증 중에 구현이 바뀌었다면 코드 기준이 달라진 것이므로 영향받은 결과도 폐기하고 다시 실행한다.

## 결과 취합
오케스트레이터가 세 보고를 **스펙 항목(`DoD-N`·`EC-N`)별로** 합친다. 아래 표를 계획 파일의 검증 기록에 남긴다.

| 스펙 항목 | 코드 대조 (`verify`) | 실행 확인 (`test-runner`·`e2e-runner`) | 종합 |
|---|---|---|---|
| DoD-1 | 충족 \| 부분 충족 \| 미충족 \| 검증 불가 | 확인됨 \| 실패 \| 미실행 + 근거 case | 충족 \| 미충족 \| 미검증 |

- 실행 확인은 항목과 연결된 case가 **assertion으로 그 조건을 검증하고 통과한 경우에만** `확인됨`이다. 테스트 통과만으로 전체 `DoD-N` 충족을 선언하지 않는다.
- 종합 `충족`은 코드 대조 `충족`과 실행 확인 `확인됨`이 모두 있을 때만 쓴다. 코드 대조가 `충족`인데 실행 근거가 없으면 `미검증`이다.
- 환경·권한·데이터 부족으로 실행하지 못한 검사는 제품 결함이 아니라 **미검증**으로 남긴다.
- 구현·테스트 작성 에이전트의 자체 검사 결과는 독립 근거로 계산하지 않는다.
- 검사한 코드 기준, 결과 요약, 근거, 미검증·실패·차단 사유를 함께 기록한다. 8단계 사용자 검토에서 미검증 범위로 제시한다.
- **실패 분류는 오케스트레이터가 한다.** 실행 에이전트는 사실(실패 case, 첫 오류, 재현 절차, 증거)만 보고하므로, 그 실패를 스펙 항목과 `verify`의 대조 결과에 맞춰 제품 결함·테스트 결함·스펙 결함으로 분류한다.

## 결과 처리
- 미충족·실패 시 **검증 역할은 제품 코드를 고치지 않는다.** 오케스트레이터가 6단계의 **원 구현 에이전트**에 재위임한다(가능하면 `SendMessage`로 기존 에이전트를 이어서, 아니면 같은 타입의 새 에이전트에 결함 보고 전문을 전달).
- 오케스트레이터가 취합 결과로 **테스트 자체의 결함**(문법·선택자·타이밍·데이터 격리 오류 등)이라고 분류한 것만 `test-dev`/`e2e-dev`에 재위임한다. 이때 검증 보고를 근거로 수정 범위를 명시하며, 테스트의 골자(`@spec` 태그, 조건 서술, 기대 결과)는 바꾸지 못한다. `verify`가 **테스트 변조**(골자 digest 불일치)를 보고하면 해당 변경을 되돌리고 같은 에이전트에 재위임한다. 테스트가 옳고 구현이 틀린 것으로 보이면 구현 에이전트에 재위임한다.
- **스펙 결함**으로 분류된 것은 사용자와 결정하고 `seongho:spec`으로 갱신한 뒤 관련 Task를 갱신해 재위임한다. 스펙이 바뀌면 `seongho:test-design`을 update로 다시 실행해 골격을 갱신·재동결한 뒤 재위임한다.
- **골자가 틀렸다**(테스트가 스펙과 다르게 쓰였다)는 판정은 에이전트가 고치지 않고 사용자와 결정한다. 합의되면 `seongho:test-design`을 update로 다시 실행한다.
- 수정 후 7단계를 다시 실행한다. 전 항목 종합 `충족` + 테스트 그린(미구현 표기로 남은 case 없음) + 프로젝트의 전체 정합성 명령 통과까지 6↔7을 반복한다. 검증이 통과하면 오케스트레이터가 계획 파일에서 검증된 Task들의 `상태`를 `완료`로 바꾼다(검증이 통과하기 전에는 `검증대기`를 유지한다).
- **수정 예산.** 오케스트레이터가 Task마다 관리한다. 최초 작성과 최초 검사는 세지 않고, 각 에이전트의 `수정 → 재검사`를 1회로 세어 **Task당 합산 3회**를 한도로 한다. 재호출·재개·에이전트 변경으로 횟수를 초기화하지 않고, 계획 파일의 해당 Task `구현 기록`에 횟수와 실패 원인을 남긴다.
- **중단 조건.** 같은 원인으로 2회 연속 진전이 없거나 한도에 도달하면 루프를 중단하고 사용자에게 스펙·계획 결함 여부를 상의한다. 한도 확대는 사용자가 명시한 경우에만 한다.
