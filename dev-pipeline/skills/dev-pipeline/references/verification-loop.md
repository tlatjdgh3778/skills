# 검증 루프 (7단계)

## 검증 에이전트 지시
새 `general-purpose` 에이전트를 띄워 Skill 도구로 `seongho:verify`를 `<스펙 경로> <계획 파일 경로>` 인자로 호출해 수행시킨다. 구현 대화를 전달하지 않는다. 지시에 명시할 것:
- (a) 어떤 파일도 수정하지 마라
- (b) 모든 판정에 근거를 붙여라
- (c) 구현을 신뢰하지 말고 깨뜨릴 방법을 먼저 찾아라

6단계에서 채워진 테스트의 실행과 판정도 이 검증이 한다(정합성 명령 단계). 계획 파일 경로를 주는 이유는 `테스트 설계 증거`의 골자 digest로 테스트 골자가 동결 상태 그대로인지 확인시키기 위해서다.

## 읽기 전용 확인
읽기 전용은 지시로만 보장되므로, 검증이 끝나면 `git status`로 검증자가 파일을 바꾸지 않았는지 확인한다. 바뀐 파일이 있으면 그 검증 결과를 폐기하고 되돌린 뒤 새 에이전트로 다시 실행한다.

## 결과 처리
- 미충족·실패 시 **검증자가 제품 코드를 고치지 않는다.** 오케스트레이터가 6단계의 **원 구현 에이전트**에 재위임한다(가능하면 `SendMessage`로 기존 에이전트를 이어서, 아니면 같은 타입의 새 에이전트에 결함 보고 전문을 전달).
- 검증 보고서가 **테스트 자체의 결함**(문법·선택자·타이밍·데이터 격리 오류 등)이라고 판정한 것만 `test-dev`/`e2e-dev`에 재위임한다. 이때 보고서를 근거로 수정 범위를 명시하며, 테스트의 골자(`@spec` 태그, 조건 서술, 기대 결과)는 바꾸지 못한다. 검증이 **테스트 변조**(골자 digest 불일치)를 보고하면 해당 변경을 되돌리고 같은 에이전트에 재위임한다. 테스트가 옳고 구현이 틀린 것으로 보이면 구현 에이전트에 재위임한다.
- **스펙 결함**으로 분류된 것은 사용자와 결정하고 `seongho:spec`으로 갱신한 뒤 관련 Task를 갱신해 재위임한다. 스펙이 바뀌면 `seongho:test-design`을 update로 다시 실행해 골격을 갱신·재동결한 뒤 재위임한다.
- **골자가 틀렸다**(테스트가 스펙과 다르게 쓰였다)는 판정은 에이전트가 고치지 않고 사용자와 결정한다. 합의되면 `seongho:test-design`을 update로 다시 실행한다.
- 수정 후 7단계를 다시 실행한다. 전 항목 충족 + 테스트 그린(미구현 표기로 남은 case 없음) + 프로젝트의 전체 정합성 명령 통과까지 6↔7을 반복한다. 검증이 통과하면 오케스트레이터가 계획 파일에서 검증된 Task들의 `상태`를 `완료`로 바꾼다(검증이 통과하기 전에는 `검증대기`를 유지한다).
- 같은 결함이 3회 반복되면 루프를 중단하고 사용자에게 스펙·계획 결함 여부를 상의한다.
