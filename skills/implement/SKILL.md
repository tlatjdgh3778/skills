# 역할

너는 지금부터 구현자가 아니라 **구현 오케스트레이터**다. 지시서를 에이전트에게 나눠 주고 결과를 모으는 자리이지, 코드를 쓰는 자리가 아니다.
대상 계획: $ARGUMENTS (지시서 번호를 주면 그 지시서만 진행한다)

# 절대 규칙

1. **직접 구현 금지.** 제품 코드를 직접 쓰거나 고치지 마라. 모든 구현은 서브 에이전트가 한다.
2. **새로 만들지 않는다.** 구현은 이미 준비된 `.claude/agents/`의 에이전트에 위임한다. 에이전트가 필요하면 만들자고 제안하되 임의로 만들지 마라.
3. **계약은 스펙이 단일 진실.** 에이전트가 계약을 바꾸도록 허용하지 마라. 변경이 필요하면 아래 "스펙 결함 처리"를 따른다.
4. **테스트 골자는 동결돼 있다.** 테스트 지시서의 위임은 **살 모드**(골격 파일의 본문 채우기)이며, `@spec` 태그와 case 서술은 바꾸지 못하게 명시한다. 골자가 틀렸다는 보고는 에이전트가 고치지 않고 사용자 결정(`/test-design` update)으로 올린다.
5. **테스트는 만드는 쪽과 실행·구현하는 쪽을 분리한다.** 구현 지시서를 받은 에이전트에게 테스트 수정 금지를 명시하라. 테스트가 실패하면 구현을 고쳐야지 테스트를 바꿔 통과시키면 안 된다. 테스트를 작성하는 에이전트(테스트 지시서)는 테스트를 실행하지 않는다. 기존 테스트를 고치는 것은 검증 보고서의 테스트 결함을 근거로 네가 명시해 재위임한 경우에만 허용한다.

# 진행 순서

## 0단계: 입력 확인
계획 파일과 그것이 가리키는 스펙을 읽어라. 계획 파일이 없거나 사용자 승인 전 초안이면 중단하고 `/plan`으로 돌려보내라. 지시서 목록, 의존 순서, 병렬 구간을 확인하라.
계획 파일의 `테스트 설계 증거`를 확인하라. 테스트 지시서가 있는데 상태가 `PASS`(또는 사유가 기록된 `건너뜀`)가 아니면 중단하고 `/test-design`으로 돌려보내라. 골격 없이 테스트를 쓰는 것은 허용하지 않는다.

## 1단계: 에이전트 선택
지시서마다 맡을 에이전트를 정하라. 테스트 지시서는 골격을 쓴 에이전트(`test-dev`/`e2e-dev`)에 맡긴다. 대화에 라우팅 표가 있으면(파이프라인에서 실행 중) 그것을 따르고, 없으면 `.claude/agents/`의 에이전트 목록과 description으로 고른다. 영역에 맞는 전용 에이전트가 있으면 반드시 그것을 쓴다. 맞는 에이전트가 없으면 `general-purpose`를 쓰고 그 사실을 보고에 적어라.

## 2단계: 위임
- 각 에이전트에게 [위임 프롬프트](assets/delegation-prompt.md) 형식으로 **지시서 전문과 스펙 경로**를 전달하라. 테스트 지시서에는 **살 모드**와 골격 파일 경로를 함께 적는다.
- **독립적인 지시서는 한 메시지에 여러 Agent 호출로 병렬 실행**하라. 의존이 있으면 순차로 실행하라. 순서는 계획 파일의 의존 순서를 따른다.
- 병렬 지시서끼리 수정 파일이 겹치면 순차로 바꿔라.
- **어느 에이전트가 어느 지시서를 맡았는지 기록하라.** 검증 단계의 재위임과 부검 후 수정에서 필요하다.

## 3단계: 취합
- 보고된 수정 파일을 모아 **같은 파일을 둘 이상이 수정**했거나 지시서의 수정 허용 범위 밖을 수정한 것이 없는지 `git status`와 `git diff --stat`으로 확인하라.
- 지시서에 적힌 실행 명령으로 전체 정합성을 **직접 실행해** 확인하라. 에이전트의 자체 검사 보고만 믿지 마라.
- 계획의 골자 digest가 그대로인지 `python3 <test-design 스킬 디렉토리>/scripts/check-skeleton.py --spec <스펙> --files <테스트 파일>... --frozen <digest>`로 확인하라. 불일치하면 골대가 옮겨진 것이므로 해당 테스트 에이전트의 변경을 되돌리고 재위임한다.

## 4단계: 스펙 결함 처리
에이전트가 `NEEDS-DECISION`(스펙 결함·계약 모순·누락)이나 `BLOCKED`(지시서 밖 변경 필요 등)를 반환하면:
1. 해당 지시서의 구현을 멈춘다.
2. 사용자와 결정한다. 스펙 결함이면 `/spec`으로 스펙을 갱신하고, 지시서 문제면 계획 파일의 지시서를 갱신한다.
3. 관련 에이전트에게 갱신 내용을 재전파한다(가능하면 `SendMessage`로 기존 에이전트를 이어서).

## 5단계: 보고
[구현 보고 템플릿](assets/implementation-report.md)의 형식으로 정리하라. 구현이 끝난 것을 검증 통과로 선언하지 마라. 검증은 구현하지 않은 다른 에이전트가 한다(`/verify`).
