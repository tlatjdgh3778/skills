# 테스트 설계 검토 기준

reviewer는 기계 검사를 통과한 것과 같은 digest의 스펙·계획·골격만 검토한다. 하나라도 `부분 충족·미충족·검증 불가`이면 PASS가 아니다. 판정은 항목마다 근거(`파일:라인`)와 함께 쓴다.

## TD-01 대상과 입력
- 스펙·계획·골격이 같은 기능을 가리킨다.
- 스펙이 확정이고 미결정 사항이 없으며, 계획이 승인됐다.
- 검토에 필요한 골격 파일이 전부 제공됐고 기계 검사의 digest와 일치한다.

## TD-02 목표와 행동 언어
- 최상위 describe가 스펙 목표를 사용자 결과의 언어로 보존한다.
- 하위 describe가 행동·상태·실패·복구의 맥락을 표현한다.
- 파일·함수·컴포넌트 이름이 행동 의미를 대체하지 않는다.

## TD-03 항목 의미와 coverage
- 모든 `DoD-N`·`EC-N`이 하나 이상의 case에 연결됐거나, 사용자가 확정한 제외 사유가 타당하다.
- 각 case의 제목과 given·when·then이 연결된 항목의 관찰 가능한 결과를 **약화하지 않는다**(예: "401" → "에러 상태").
- 한 항목에 독립 결과가 여럿이면 필요한 만큼 case가 나뉘었다.
- 스펙에 없는 요구·수치·자동 복구·권한·성능 기준을 추가하지 않았다(**부풀림**).

## TD-04 실패·경계·복구
- 스펙이 요구한 정상·빈 상태·실패·중간 오류·복구·동시성 경계가 포함됐다.
- 비목표를 기능으로 추가하지 않았다.
- 구현이 실제로 틀렸을 때 **실패할 수 있는** 의미를 갖는다(어떻게 구현해도 통과하는 서술이 아니다).

## TD-05 테스트 층과 파일 배치
- 단위·통합·E2E 분류가 검증하려는 결과와 맞는다.
- 여러 화면·상태·API 경계를 잇는 핵심 사용자 흐름은 E2E 골격이 있거나 사람이 승인한 제외 근거가 있다.
- 같은 의미를 여러 층에서 불필요하게 중복하지 않는다.
- 구현 전에는 알 수 없는 selector·fixture·내부 구조를 골격에 발명하지 않았다.

## TD-06 mock·실제 연동 경계
- mock이 핵심 비즈니스 로직·상태 전이를 우회하지 않는다.
- mock으로 증명할 수 없는 것(인증, 실제 비동기 계약, 부하, 환경 차이)이 실제 연동 검증으로 분리됐거나 미검증으로 명시됐다.
- mock PASS를 실제 서버·운영 PASS로 확대하지 않는다.
- 사람 결정이 필요한 경계를 숨기지 않는다.

## TD-07 책임과 상태
- 모든 case가 미구현 표기이며 기능 통과로 보고되지 않는다.
- assertion·제품 코드·fixture·mock handler·selector 구현이 섞이지 않았다.
- 구현 단계가 바꿀 수 있는 것(본문)과 바꿀 수 없는 것(골자: 태그와 서술)이 구분된다.

## 판정
- `PASS`: 모든 항목 충족, finding·미검사·사람 결정 없음
- `NEEDS-FIX`: 기존 스펙·계획·골격 계약만으로 수정 가능
- `NEEDS-DECISION`: mock 경계, 제외 항목, 고위험·검증 불가, 새 제품 결정 필요
- `REVIEW-BLOCKED`: 필수 입력·digest·격리 문제
- `NOT-RUN`: 필수 항목 일부 미실행

Finding은 `TD-F001` 형식의 ID, 관련 항목 ID·파일 위치, 판정, 문제, 근거, 필요한 결과를 포함한다. reviewer는 수정안을 제품 결정으로 확장하지 않고 파일을 직접 수정하지 않는다.
